# 可靠数据传输(RDT)协议模拟器——实验实操指南

---

## 一、模拟器怎么用、模拟的是什么

### 1.1 模拟的是什么

这个模拟器复现了两台机器通过**数据链路层协议**进行通信的过程。它创建了三个进程：

```
┌─────────────────────────────────────────────┐
│                  main 进程                   │
│           (时钟控制 + 调度 + 死锁检测)         │
│                                              │
│   每次 tick 选择 M0 或 M1 写入当前时间         │
│   收到回复 OK → 继续；连续 NOTHING → 死锁      │
└───────┬──────────────────────┬──────────────┘
        │ 管道 w3→r3 (时钟)     │ 管道 w5→r5 (时钟)
        │ 管道 r4→w4 (状态回复)  │ 管道 r6→w6 (状态回复)
        ▼                       ▼
┌───────────────┐       ┌───────────────┐
│    M0 (发送方)  │ 管道   │    M1 (接收方)  │
│  运行协议函数   │◄══════►│  运行协议函数   │
│               │w1→r1   │               │
│  id = 0       │w2←r2   │  id = 1       │
└───────────────┘       └───────────────┘
```

**模拟的不是真实网络**，而是在一个进程里用**随机数**模拟信道的三种损伤：

| 损伤类型 | 如何模拟 | 对应参数 |
|----------|----------|----------|
| 丢帧 | 发送时以概率直接丢弃，不写入管道 | `pct_loss` (0-99) |
| 帧损坏(校验和错) | 接收时以概率标记为 cksum_err | `pct_cksum` (0-99) |
| 超时 | 定时器到期触发 timeout 事件 | `timeout` (tick 数) |

每次仿真运行，M0 和 M1 各自运行协议代码，通过 `wait_for_event()` 等库函数与模拟器框架交互。仿真结束时输出统计信息：发送帧数、丢失帧数、重传帧数、成功交付的有效载荷数、效率等。

### 1.2 怎么用

**第一步：编译**

```bash
make
```

生成可执行文件 `sim`。

**第二步：运行**

```bash
./sim <protocol> <events> <timeout> <pct_loss> <pct_cksum> <debug_flags>
```

6 个参数全部必填，含义如下：

| 位置 | 参数 | 含义 | 取值范围 |
|------|------|------|----------|
| 1 | `protocol` | 要运行的协议编号 | 2 ~ 6 |
| 2 | `events` | 仿真事件总数（决定运行时长） | 正整数，如 10000 |
| 3 | `timeout` | 超时间隔，单位是 tick | 正整数，如 10 |
| 4 | `pct_loss` | 丢包百分比 | 0 ~ 99 |
| 5 | `pct_cksum` | 校验和错误百分比 | 0 ~ 99 |
| 6 | `debug_flags` | 调试输出标志位 | 见下表 |

**debug_flags 含义**（可叠加，如 `3` = 1+2 同时打开发送和接收）：

| 值 | 含义 |
|----|------|
| 0 | 静默模式，只输出最终统计 |
| 1 | 打印每帧发送 |
| 2 | 打印每帧接收 |
| 4 | 打印每次超时 |
| 8 | 周期性输出（长时间运行用） |

**典型示例：**

```bash
# 协议6(GBN), 10万事件, 超时40tick, 丢包20%, 校验错10%, 打印收发
./sim 6 100000 40 20 10 3

# 协议3(PAR), 无差错信道, 查看帧收发过程
./sim 3 1000 10 0 0 3

# 协议5(GBN), 高丢包场景, 周期性输出统计
./sim 5 50000 50 30 0 8
```

**关键的输出指标：**

```
Efficiency (payloads accepted/data pkts sent) = XX%
```

- 效率 = 成功交付的有效载荷数 / 发送的数据帧总数
- 这是衡量协议性能的核心指标

## 二、实验完整流程 & 每个阶段关注什么

### 阶段 0：环境准备

- 将整个 `simulator/` 目录复制到 Ubuntu 24.04 虚拟机
- 确保安装了 `gcc` 和 `make`：

```bash
sudo apt install build-essential
```

### 阶段 1：编译 & 初步运行

```bash
cd simulator
make
```

编译成功后先跑一条简单命令验证：

```bash
./sim 2 1000 10 0 0 1
```

如果编译报错——这是**大概率事件**。这份代码写于 1996 年，针对的是 32 位系统 + 老式 C 标准（K&R 风格函数声明、`sys/stat.h` 而非 `sys/stat.h` + POSIX 宏等），在 Ubuntu 24.04 64 位 + gcc 13 下几乎必然有兼容性问题。**把完整报错贴给我，我来定位和修复。**

常见报错类型预估（不限于此）：
- 隐式函数声明（缺少 `#include <stdlib.h>` 等）
- `sys/stat.h` 路径问题（需改为 `sys/stat.h` 且可能需定义 `_POSIX_SOURCE`）
- 指针/整数转换警告变错误（64 位下 `int` 和指针大小不同）
- K&R 风格函数定义不被接受
- `sleep()` / `write()` / `read()` 等缺少头文件

### 阶段 2：理解各协议行为（重点阶段）

这个阶段的目标是**逐协议跑、对比观察**，理解每种协议的运行特征。建议按协议号顺序来。

#### 协议 2（停等协议）
```bash
./sim 2 1000 10 0 0 3
```

- **关注点**：发送一帧 → 等待接收方返回哑 ACK → 再发下一帧。丢包率为 0，所以效率应该接近 100%。
- **本质**：这不是真正解决丢包，而是解决**流控**——接收方处理不过来时不让发送方继续发。

#### 协议 3（PAR，肯定确认重传）
```bash
# 无差错
./sim 3 1000 10 0 0 3
# 有丢包
./sim 3 1000 10 20 0 3
# 丢包 + 校验错
./sim 3 1000 10 20 10 3
```

- **关注点**：
  - 1 位序列号（seq=0/1）如何交替
  - 超时后重传的行为
  - 收到损坏帧时直接丢弃，等待发送方超时重传
  - 改变 `timeout` 值对效率的影响（timeout 太短 → 不必要重传；太长 → 等待浪费）

#### 协议 4（滑动窗口，双向）
```bash
./sim 4 1000 20 10 0 3
```

- **关注点**：
  - M0 和 M1 同时收发（双向通信，不再区分"发送方"和"接收方"）
  - **捎带确认 (piggybacking)**：ACK 搭载在反向数据帧里而非单独发
  - 仍然是 1 位序列号，窗口大小为 1

#### 协议 5（Go-Back-N，流水线）
```bash
# 基准——无差错
./sim 5 10000 50 0 0 3
# 有丢包
./sim 5 10000 50 20 0 3
# 有校验错
./sim 5 10000 50 0 10 3
# 恶劣信道
./sim 5 10000 50 30 20 3
```

- **关注点**：
  - MAX_SEQ=7，最多 7 帧在路上（流水线）
  - `network_layer_ready` 事件：网络层准备好才取包，不是随时都有数据
  - 超时后**回退 N 帧**：`next_frame_to_send = ack_expected`，把所有未确认的帧重发一遍
  - 接收方**只按序接收**，乱序帧直接丢弃
  - 与协议 3 对比：同样的丢包率下，GBN 的吞吐量高得多（因为不用等）

#### 协议 6（Selective Repeat，选择重传）
```bash
# 基准——无差错
./sim 6 10000 50 0 0 3
# 有丢包
./sim 6 10000 50 20 0 3
# 恶劣信道
./sim 6 10000 50 30 20 3
```

- **关注点**：
  - MAX_SEQ=7，但窗口大小 NR_BUFS = 4（= (7+1)/2，SR 的窗口 ≤ 序列号空间一半）
  - 每帧有**独立定时器**，超时只重传那一帧而非全部
  - 接收方**乱序缓存**、**按序交付**：`arrived[]` 数组标记哪些帧已收到
  - **NAK 机制**：收到预期之外的帧或校验错时发 NAK 请求重传特定帧
  - **独立 ACK 定时器**：收到帧后不立即回 ACK，等一个较短的 ack_timer，看能否捎带确认

### 阶段 4：源码修改实验（exercises 选题 3-6）

#### 选题 3 — 修改事件优先级

修改 `worker.c` 中 `pick_event()` 函数里各 case 的检测顺序。比如把协议 5 的 timeout 检测提到 frame_arrival 之前：

```c
// 原顺序：nframes > 0 → 先返回 frame_arrival
// 改后：先 check_timers → 先返回 timeout
```

对比修改前后协议行为的变化，得出关于**事件优先级设计**的结论。

#### 选题 4 — 最优超时研究

系统性地变化 timeout 值，记录重传帧数量。找出重传数最小的 timeout 区间。

#### 选题 5 — 优化时钟推进

当前模拟器每次 tick 都+DELTA(10)，即使两个进程都阻塞在远距离超时上也是慢慢爬。修改使得当 `lowest_timer` 远大于当前 tick 时，直接跳到 `lowest_timer`。

**修改位置**：`sim.c` 的 main loop 中 tick 推进逻辑，以及 `worker.c` 的 `wait_for_event()`。

#### 选题 6 — 引入可变传输时延

当前帧一旦写入管道就算"瞬时到达"。修改让每个帧携带一个随机延迟值，接收方在该延迟后才处理。

## 三、关于代码兼容性

这份代码来自 1996 年，伴随 Tanenbaum《计算机网络》第三版发布。代码特征：

- 32 位 UNIX 时代的编码风格
- K&R 风格的部分函数声明（如 `void main()` 而非 `int main()`）
- 依赖 `<sys/stat.h>` 等老式头文件
- `int` 和指针混用，在 64 位下可能出问题
- Makefile 中 `CFLAGS=-D_POSIX_SOURCE`，现代 gcc 可能需要调整

**对策**：我们不在编译前猜测所有 bug。你在 Ubuntu 24.04 上 `make` 后，**把完整的错误输出贴给我**，我根据具体报错逐条修复。修复原则：

1. 最小改动——只改报错的地方，不做"顺手重构"
2. 不改变协议逻辑——只让它在现代环境下能编译运行
3. 每修一处都解释为什么要这样改

## 四. 协议 1 → 6 的演化路线

模拟器中的六个协议不是六个孤立的方案，而是一条**逐步演化的设计链**。每个协议在前一个的基础上增加一项新能力，解决一个现实问题。

### 演化全景

```
协议1 ──(加流控)──► 协议2 ──(加差错控制)──► 协议3 ──(改双向+捎带确认)──► 协议4
                                                                          │
                                                          ┌───────────────┘
                                                          ▼
                                              协议5 ──(改选择重传)──► 协议6
                                            (流水线+GBN)          (SR+NAK+独立定时器)
```

### 逐级变化详解

#### 协议 1 → 协议 2：从"无流控"到"有流控"

| 对比维度 | 协议 1（乌托邦） | 协议 2（停等） |
|----------|-----------------|---------------|
| 信道假设 | 无差错 | 无差错（不变） |
| 发送方行为 | 死循环一直发，不等待 | 发一帧 → 等待确认 → 再发下一帧 |
| 接收方行为 | 收到就递交给网络层 | 收到后**回发一个哑帧**（dummy frame）唤醒发送方 |
| 事件类型 | `frame_arrival` | `frame_arrival`（不变） |

**协议 1 的问题**：假设接收方处理速度无限快，现实中不可能。发送方无节制地发帧，接收方缓冲区会被撑爆。

**协议 2 的解决方案**：接收方每收到一帧，回发一个哑帧作为"确认收到，可以发下一帧了"的信号。这就是最原始的**流量控制（Flow Control）**——用确认机制限制发送速率。

> 关键变化：**发送方多了 `wait_for_event(&event)` 调用**，接收方多了 `to_physical_layer(&s)` 回发哑帧。

```c
// 协议 1 发送方：疯狂发，不等人
while (true) {
    from_network_layer(&buffer);
    to_physical_layer(&s);       // 发完立刻取下一包，不管对方收没收到
}

// 协议 2 发送方：发完必须等
while (true) {
    from_network_layer(&buffer);
    to_physical_layer(&s);
    wait_for_event(&event);      // ← 新增：等接收方回了确认再继续
}
```

#### 协议 2 → 协议 3：从"无差错信道"到"不可靠信道"

| 对比维度 | 协议 2（停等） | 协议 3（PAR/交替位） |
|----------|---------------|---------------------|
| 信道假设 | 无差错 | **不可靠**：帧可能丢失、可能损坏 |
| 序列号 | 无 | **1 位序号**（seq=0/1 交替） |
| 确认机制 | 哑帧（内容无意义） | **确认帧带 ack 字段**，告知期望的下一个序号 |
| 定时器/重传 | 无 | **有**：发帧后启动定时器，超时未确认则重传 |
| 事件类型 | `frame_arrival` | `frame_arrival`、**`cksum_err`**、**`timeout`** |
| 宏定义 | 无 | **`MAX_SEQ 1`** |

**协议 2 的问题**：假设信道完美——帧不丢、不坏。真实网络中丢帧和损坏是常态，协议 2 在丢帧时会**永久阻塞**（发送方等确认，确认永远到不了）。

**协议 3 的解决方案——三件武器**：

1. **序号（seq）**：给每帧编号 0 或 1，接收方据此区分"新帧"和"重传的旧帧"。
2. **确认号（ack）**：接收方在确认帧中写入 `1 - frame_expected`，告诉发送方"我已收到序号 X 的帧，期待序号 1-X"。
3. **定时器（timer）**：发帧后启动定时器，超时未收到正确确认则重传。

```c
// 协议 3 发送方核心逻辑
s.seq = next_frame_to_send;          // ← 新增：给帧打上序号
to_physical_layer(&s);
start_timer(s.seq);                  // ← 新增：启动定时器
wait_for_event(&event);              // 现在有三种可能事件
if (event == frame_arrival) {
    from_physical_layer(&s);
    if (s.ack == next_frame_to_send) {  // ← 新增：确认号匹配检查
        stop_timer(next_frame_to_send);
        inc(next_frame_to_send);       // 序号翻转为对方期望的下一个
    }
}
// 如果 event == timeout，循环回到开头自动重传
```

#### 协议 3 → 协议 4：从"单向通信"到"双向通信 + 捎带确认"

| 对比维度 | 协议 3（PAR） | 协议 4（滑动窗口） |
|----------|-------------|-------------------|
| 通信方向 | **单向**（sender → receiver） | **双向**（双方同时收发） |
| 代码结构 | 两个独立函数 `sender3()` + `receiver3()` | **单个函数** `protocol4()` 包含收发两端 |
| 确认方式 | 单独发送 Ack 帧 | **捎带确认（Piggybacking）**：Ack 搭载在反向数据帧里 |
| 序列号空间 | MAX_SEQ=1 | MAX_SEQ=1（不变） |
| 窗口大小 | 1 | 1（不变） |

**协议 3 的问题**：只能单向发数据。反向链路只用来传 Ack，浪费了带宽。

**协议 4 的解决方案**：
- 双方都既能发数据也能收数据，不再区分"发送方"和"接收方"角色。
- **捎带确认**：`s.ack = 1 - frame_expected` 直接写在每个发出的数据帧里，不用单独发 Ack 帧。帧同时携带自己的 seq（作为数据帧的序号）和 ack（确认对方的数据）。

```c
// 协议 4：一帧两用
s.seq = next_frame_to_send;          // 我发的数据的序号
s.ack = 1 - frame_expected;          // 我期望从你那里收到的下一个序号（捎带确认）
to_physical_layer(&s);
```

> 这次变化的核心不是增加新机制，而是**合并角色**——把协议 3 中分离的 sender 和 receiver 合并到一个循环里，用捎带确认提升效率。

#### 协议 4 → 协议 5：从"停等"到"流水线（Go-Back-N）"

| 对比维度 | 协议 4（滑动窗口） | 协议 5（GBN） |
|----------|-------------------|--------------|
| MAX_SEQ | 1 | **7**（3 位序号） |
| 窗口大小 | 1（路上最多 1 帧） | **7**（路上最多 7 帧） |
| 数据来源 | 假设网络层总有数据 | **按需取包**：网络层有数据才触发 `network_layer_ready` |
| 事件类型 | `frame_arrival, cksum_err, timeout` | **+ `network_layer_ready`** |
| 缓冲区 | 单个 `packet buffer` | **`packet buffer[MAX_SEQ+1]`** 数组 |
| 重传策略 | 单帧 | **回退 N 帧**：超时后重发所有未确认帧 |
| 辅助函数 | 无 | **`between()`** 环形序号比较、**`send_data()`** 构造并发送帧 |
| 流控 | 无 | **`enable/disable_network_layer()`** 窗口满时阻止网络层给数据 |

**协议 4 的问题**：窗口大小只有 1，发一帧等一帧，信道利用率极低——大量时间花在等待上。

**协议 5 的解决方案——两大突破**：

1. **流水线（Pipelining）**：窗口扩大到 7，可以连续发 7 帧不等确认，信道利用率大幅提升。
2. **按需取数据**：不再假设网络层总有数据。用 `network_layer_ready` 事件通知"有数据可取了"，窗口满时用 `disable_network_layer()` 阻止网络层再给数据。

```c
// 协议 5 超时处理：回退 N 帧
case timeout:
    next_frame_to_send = ack_expected;    // 退回最早的未确认帧
    for (i = 1; i <= nbuffered; i++) {
        send_data(next_frame_to_send, frame_expected, buffer);  // 全部重发
        inc(next_frame_to_send);
    }
```

**协议 5 的代价**：一旦超时，所有窗口内未确认的帧全部重发——包括那些其实已经被正确接收的帧。浪费带宽。

#### 协议 5 → 协议 6：从"回退 N 帧"到"选择重传（Selective Repeat）"

| 对比维度 | 协议 5（GBN） | 协议 6（SR） |
|----------|-------------|-------------|
| MAX_SEQ | 7 | 7（不变） |
| 窗口大小 | 7 | **4**（= (MAX_SEQ+1)/2，SR 必须 ≤ 序号空间的一半） |
| 事件类型 | `frame_arrival, cksum_err, timeout, network_layer_ready` | **+ `ack_timeout`** |
| 帧类型 | 只有 data 帧 | **data、ack、nak 三种帧**（`frame_kind` 枚举） |
| 重传策略 | 回退所有未确认帧 | **只重传超时的那一帧** |
| 接收方乱序处理 | **丢弃乱序帧** | **缓存乱序帧**（`arrived[]` 位图 + `in_buf[]` 缓冲区） |
| 定时器 | 整个窗口一个逻辑定时器 | **每帧独立定时器** |
| 确认时机 | 收到帧立即确认 | **延迟确认**：`ack_timer` 到期后才发单独 Ack（等待捎带机会） |
| 否定确认 | 无 | **NAK 机制**：收到意外帧或损坏帧时主动请求重传特定帧 |

**协议 5 的问题**：

1. 超时后全部重传，浪费带宽（已经被正确接收的帧也被重传）。
2. 接收方丢弃乱序帧，正确但已乱序到达的帧白白浪费。

**协议 6 的解决方案——五项精进**：

1. **每帧独立定时器 + 精确重传**：超时时只重传 `oldest_frame`（最早超时的那个），不影响其他帧。
   ```c
   case timeout:
       send_frame(data, oldest_frame, frame_expected, out_buf);  // 只重传一帧！
   ```

2. **乱序接收 + 按序交付**：接收方维护 `arrived[]` 位图，乱序到达的帧先缓存到 `in_buf[]`。一旦 contiguously 收到的帧连成一片，批量递交给网络层。
   ```c
   arrived[r.seq % NR_BUFS] = true;               // 缓存乱序帧
   while (arrived[frame_expected % NR_BUFS]) {     // 连续交付
       to_network_layer(&in_buf[frame_expected % NR_BUFS]);
       inc(frame_expected);
   }
   ```

3. **NAK（否定确认）**：收到校验错帧或非预期的帧时，立即发 NAK 请求对方重传特定帧，而不干等超时。
   ```c
   case cksum_err:
       if (no_nak) send_frame(nak, 0, frame_expected, out_buf);  // 主动通知对方
   ```

4. **延迟确认（ack_timer）**：收到帧后不立即回 Ack，等一个较短的 `ack_timer`。如果这期间有反向数据帧要发，Ack 就可以捎带出去，省掉单独 Ack 帧的开销。
   ```c
   case ack_timeout:
       send_frame(ack, 0, frame_expected, out_buf);  // 实在等不到了，发单独 Ack
   ```

5. **窗口减半**：NR_BUFS = 4，因为 SR 要求窗口大小 ≤ 序号空间的一半，否则新旧帧无法区分。

### 总结：六个协议对应六个现实问题

| 协议 | 要解决的问题 | 引入的机制 |
|------|-------------|-----------|
| 协议 1 | 最基础的帧传输 | 发帧、收帧、递交给网络层 |
| 协议 2 | 接收方处理速度有限（流控） | 确认帧（哑帧），发送方发后等待 |
| 协议 3 | 信道不可靠（丢帧、损坏） | 序号 + 确认号 + 定时器 + 超时重传 |
| 协议 4 | 单向通信浪费反向信道 | 双向通信 + 捎带确认（Piggybacking） |
| 协议 5 | 停等协议信道利用率低 | 流水线 + 滑动窗口 + 回退 N 帧（GBN） |
| 协议 6 | GBN 全部重传浪费带宽 | 选择重传 + 乱序缓存 + NAK + 独立定时器 + 延迟确认 |

**一句话**：协议 1→3 解决**可靠性**问题（从"假设完美"到"应对不完美"），协议 4 解决**双向利用**问题，协议 5→6 解决**效率**问题（从"停等"到"流水线"再到"精确重传"）。
